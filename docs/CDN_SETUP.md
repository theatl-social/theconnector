# CDN Setup for Vite Assets

This document explains how to configure CDN support for Vite-generated assets in TheConnector.

## Overview

TheConnector supports serving all Vite-generated assets (JavaScript, CSS, fonts, images) from a CDN. This is accomplished through a combination of build-time configuration and runtime Rails integration.

## Quick Start

### For Docker Builds

Set the `CDN_HOST` build argument when building your Docker image:

```bash
docker build --build-arg CDN_HOST=https://cdn.example.com -t theconnector .
```

### For Manual Deployment

1. Set the `CDN_HOST` environment variable during asset compilation:

```bash
CDN_HOST=https://cdn.example.com yarn build:production
```

2. Configure Rails to use the same CDN host in `config/environments/production.rb`:

```ruby
config.asset_host = ENV['CDN_HOST'] if ENV['CDN_HOST'].present?
```

(This is already configured in TheConnector)

## How It Works

### Architecture

CDN support uses a **hybrid approach** with two mechanisms:

1. **CSS Assets**: Absolute CDN URLs baked into CSS files at build time
2. **JavaScript & Manifest**: Relative paths resolved at runtime

### Detailed Flow

#### 1. Build Time (Vite)

When `CDN_HOST` is set during build:

```bash
CDN_HOST=https://cdn.example.com yarn build:production
```

Vite's `base` configuration (in `vite.config.mts`) is set to:

```typescript
const base = isProdBuild && cdnHost ? `${cdnHost}/packs/` : `/packs/`;
```

**What Vite Generates:**

- **CSS files**: Contain absolute CDN URLs for fonts/images

  ```css
  @font-face {
    src: url(https://cdn.example.com/packs/assets/roboto-bold.woff2);
  }
  ```

- **JavaScript files**: Contain relative import paths

  ```javascript
  import('../chunk-ABC123.js');
  import('./component-XYZ456.js');
  ```

- **Manifest.json**: Contains relative paths
  ```json
  {
    "app/javascript/mastodon/main.tsx": {
      "file": "assets/application-D7EesDm0.js"
    }
  }
  ```

#### 2. Runtime (Rails)

Rails' `vite_helper` (from `vite_rails` gem) reads the manifest and combines relative paths with `config.asset_host`:

```ruby
# config/environments/production.rb
config.asset_host = ENV['CDN_HOST']  # e.g., "https://cdn.example.com"
```

**Rails generates HTML like:**

```html
<script src="https://cdn.example.com/packs/assets/application-D7EesDm0.js"></script>
<link
  href="https://cdn.example.com/packs/assets/themes/default-CYBDZWp7.css"
  rel="stylesheet"
/>
```

#### 3. Browser Resolution

When the browser loads assets from the CDN:

1. **Initial load**: Browser fetches main JS/CSS from CDN URLs (generated by Rails)

2. **Dynamic imports**: Browser resolves relative imports relative to the current script's CDN location
   - Script at: `https://cdn.example.com/packs/assets/application.js`
   - Import: `import("../chunk-ABC.js")`
   - Resolves to: `https://cdn.example.com/packs/chunk-ABC.js` ✅

3. **CSS assets**: Already contain absolute CDN URLs, load directly from CDN

### Asset Types Coverage

All asset types are CDN-compatible:

| Asset Type               | CDN URL Method                   | Example                                                   |
| ------------------------ | -------------------------------- | --------------------------------------------------------- |
| CSS files                | Rails manifest resolution        | `https://cdn.example.com/packs/assets/themes/default.css` |
| JavaScript bundles       | Rails manifest resolution        | `https://cdn.example.com/packs/assets/application.js`     |
| JavaScript chunks        | Browser relative resolution      | `https://cdn.example.com/packs/chunk-ABC.js`              |
| Fonts (woff2, woff, ttf) | Absolute URLs in CSS             | `url(https://cdn.example.com/packs/assets/roboto.woff2)`  |
| Images (png, svg, jpg)   | Absolute URLs in CSS OR manifest | `url(https://cdn.example.com/packs/assets/logo.png)`      |
| Locale files             | Browser relative resolution      | `https://cdn.example.com/packs/intl/en.js`                |
| Service Worker           | Manifest resolution              | `https://cdn.example.com/packs/sw.js`                     |

## Configuration

### Vite Configuration

Located in `vite.config.mts`:

```typescript
export const config: UserConfigFnPromise = async ({ mode, command }) => {
  const isProdBuild = mode === 'production' && command === 'build';
  const cdnHost = process.env.CDN_HOST;

  const base =
    isProdBuild && cdnHost
      ? `${cdnHost}/${outDirName}/` // e.g., "https://cdn.example.com/packs/"
      : `/${outDirName}/`; // e.g., "/packs/"

  return {
    base,
    // ... other config
  };
};
```

### Rails Configuration

Located in `config/environments/production.rb`:

```ruby
# Enable serving of images, stylesheets, and JavaScripts from an asset server.
config.asset_host = ENV['CDN_HOST'] if ENV['CDN_HOST'].present?
```

### Dockerfile Configuration

The `CDN_HOST` build argument is passed through to the asset compilation step:

```dockerfile
ARG CDN_HOST=""

# ... later in build stage ...

RUN \
  # Use Ruby on Rails to create Mastodon assets
  CDN_HOST="${CDN_HOST}" \
  bundle exec rails assets:precompile;
```

## Testing

### Automated Testing

The CI workflow `.github/workflows/test-cdn-assets.yml` validates CDN configuration:

1. **Manifest Structure**: Verifies manifest.json exists and contains relative paths
2. **Dynamic Imports**: Analyzes JavaScript bundles for correct relative import patterns
3. **CSS Assets**: Checks CSS files for asset references
4. **Directory Structure**: Validates build output organization
5. **Backward Compatibility**: Ensures builds work without CDN_HOST

Run tests locally:

```bash
# Build with CDN
CDN_HOST=https://cdn-test.example.com yarn build:production

# Verify manifest
cat public/packs/.vite/manifest.json | jq '.["app/javascript/mastodon/main.tsx"]'

# Check CSS for CDN URLs
grep -o 'url(https://cdn-test.example.com[^)]*' public/packs/assets/*.css | head -5
```

### Manual Testing

1. **Build with CDN enabled**:

   ```bash
   CDN_HOST=https://your-cdn.example.com yarn build:production
   ```

2. **Verify CSS contains absolute CDN URLs**:

   ```bash
   grep -r "https://your-cdn.example.com" public/packs/assets/*.css
   ```

3. **Verify manifest contains relative paths**:

   ```bash
   cat public/packs/.vite/manifest.json | head -20
   # Should show paths like "assets/application-XXX.js", NOT full URLs
   ```

4. **Deploy and check browser**:
   - Open browser DevTools → Network tab
   - Verify all assets load from your CDN domain
   - Check that there are no 404 errors for chunks/fonts

## Deployment

### Docker Deployment

```bash
# Build with CDN support
docker build \
  --build-arg CDN_HOST=https://cdn.example.com \
  -t theconnector:latest \
  .

# Run container
docker run -d \
  -e CDN_HOST=https://cdn.example.com \
  theconnector:latest
```

**Important**: Set `CDN_HOST` in both:

1. Build argument (for Vite build)
2. Runtime environment variable (for Rails)

### Manual Deployment

```bash
# 1. Set environment variable
export CDN_HOST=https://cdn.example.com

# 2. Build assets
yarn build:production

# 3. Precompile Rails assets (if needed)
bundle exec rails assets:precompile

# 4. Deploy built assets to your CDN
# (Copy public/packs/* to your CDN storage)

# 5. Start Rails with CDN_HOST set
CDN_HOST=https://cdn.example.com bundle exec rails server
```

## Troubleshooting

### Assets not loading from CDN

**Symptom**: Browser loads assets from origin server instead of CDN

**Causes & Solutions**:

1. **CDN_HOST not set during build**

   ```bash
   # Rebuild with CDN_HOST
   CDN_HOST=https://cdn.example.com yarn build:production
   ```

2. **CDN_HOST mismatch between build and runtime**

   ```bash
   # Ensure the same CDN_HOST value is used for both
   echo $CDN_HOST  # Should match your build-time value
   ```

3. **CSS files have relative paths instead of absolute**
   ```bash
   # Check if CSS was built with CDN_HOST
   grep "url(https://cdn" public/packs/assets/*.css
   # If this is empty, rebuild with CDN_HOST set
   ```

### JavaScript chunks fail to load (404 errors)

**Symptom**: Main app loads but dynamic chunks return 404

**Cause**: Incorrect relative path resolution

**Debug**:

```bash
# Check if chunks are in the expected location
ls -la public/packs/assets/
ls -la public/packs/intl/

# Verify CDN is serving from the /packs/ prefix
curl https://your-cdn.example.com/packs/assets/application-XXX.js
```

**Solution**: Ensure your CDN serves files from the `/packs/` path, not the root.

### Fonts not loading

**Symptom**: Text displays in fallback fonts, console shows font 404 errors

**Debug**:

```bash
# Check CSS for font URLs
grep "@font-face" public/packs/assets/*.css -A 5

# Verify fonts exist in build output
ls -la public/packs/assets/*.woff2
```

**Solution**:

1. Verify CDN_HOST was set during build
2. Ensure font files are uploaded to CDN
3. Check CDN CORS headers allow font loading

## Advanced

### Custom CDN Path Prefix

If you need assets at a different path (not `/packs/`), modify `vite.config.mts`:

```typescript
const customPath = process.env.CDN_PATH || 'packs';
const base =
  isProdBuild && cdnHost ? `${cdnHost}/${customPath}/` : `/${customPath}/`;
```

### Multiple CDN Domains

For serving different asset types from different CDNs, you'll need to customize the Vite plugins and Rails helpers. This is not currently supported out-of-the-box.

### CDN with Cloudflare

Cloudflare works seamlessly with this setup:

```bash
# Build with Cloudflare CDN
CDN_HOST=https://assets.yoursite.com docker build -t theconnector .
```

Configure Cloudflare to:

1. Cache static assets (JS, CSS, fonts, images)
2. Set appropriate cache headers
3. Enable Brotli compression

### CDN with AWS CloudFront

```bash
# Build with CloudFront distribution
CDN_HOST=https://d1234567890.cloudfront.net docker build -t theconnector .
```

Upload `public/packs/*` to your S3 bucket, then CloudFront will serve them.

## Backward Compatibility

**Building without CDN_HOST is fully supported:**

```bash
# Build without CDN - uses relative paths
yarn build:production
```

Assets will be served from the origin server at `/packs/` paths. This is useful for:

- Development environments
- Self-hosted instances without a CDN
- Testing
